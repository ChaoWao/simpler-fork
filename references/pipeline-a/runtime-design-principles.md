# Simpler 运行时总体原则

本文记录架构与评审的总体原则，适用于 TMR / HBG、program / kernel 以及 eager / capture 的设计。
这些是目标约束，不表示当前主线已经全部实现，也不是 Pipeline A 的完整前置任务清单。

- [Pipeline A 如何应用这些原则](run-pipeline-track-a.md#principles-application)：本轨必须兑现的合同与验收。
- [Workspace 分类核查](workspace-memory-principles.md)：实际内存对象、写入方和最后使用者。
- [A 轨任务 DAG](run-pipeline-track-a.html#roadmap)：A 轨及并行支线的交付关系；不代表全部总体架构工作。

## 一、架构与接口

### G1. Program / kernel 共用执行核心

Simpler 提供统一的准备与异步执行能力。Kernel 模式的输入输出存储由外部框架管理；
program 模式在外层增加独立运行所需的输入输出管理和必要的数据搬运。两者共用内部 workspace、
代码驻留及设备执行协议，不复制整套 API 后仅增加 kernel 后缀。

Kernel 模式不要求所有内部内存由调用方分配；program 模式也不要求每次都搬运 tensor。
设备 / context 生命周期和 reset 权限由外层合同明确，借用模式不能擅自 reset 或接管外部资源。
Program / kernel 与 eager / capture 是不同维度，不能以当前入口或 stream 数量定义永久架构。

### G2. 调用描述按值交付，存储和 handle 的寿命明确

PyPTO 向 simpler 交付调用描述与参数值，不把临时 host 对象的所有权隐式转交给 simpler。
接口须定义消费边界；该边界之后，simpler 若仍需这些字节，应持有自己的快照。
复制 tensor 描述符不等于复制 tensor 数据；host / device tensor 的实际存储另有借用合同。
异步上传仍引用调用方 host buffer 时，必须明确借用期限，不能声称已完成值交付。

外部框架管理的 device tensor、输出和 cache 只借用地址，不接管分配释放。
Simpler 自行创建的 staging 是内部资源。Device 资源通过 handle 交付时，明确谁控制生命周期、
谁执行释放，以及任务和 graph 的引用何时解除；不能从“返回了 handle”推断已经可以回收。

## 二、资源、执行与重放

### G3. 内部资源统一管理，数量与字节额度分开

内部资源须有明确所有者、分配失败处理、复用边界和最后消费者记账。L2/L3 的 workspace 寿命管理不以用户设置硬上限为前提：按实际需求分配，容量足够则复用，扩容失败保全仍有效的旧计划。L2 高频路径可准备并复用容量，L3 按需求分配；不能因此忽略在途消费者或透明替换其地址。

普通异步的目标接口默认按实际资源自动准入与背压，不要求用户设置pipeline_depth、pending_run_depth、launch_depth或grant。内部资源数量、设备提交状态、workspace字节和DFX保留仍分别核算；内部维度不应机械地成为公共配置。调用者确需主动限额时才提供可选策略，数量也不保证任意尺寸分配成功。

资源可复用或可安全增长时接受并尽早提交；被在途消费者占用且有明确释放来源时等待；单请求不可满足、无释放来源的分配失败或停止未知分别明确报错/隔离。不得无限积压host请求、反复malloc试探OOM或依赖瞬时空闲内存承诺成功。多资源预留、回滚、释放通知及无死锁等待必须一并设计。当前main仍保留显式depth机制，该目标尚未实现；兼容迁移须明确旧参数与默认行为。

预算启用时必须写清覆盖区域、旧代保留与扩容峰值；host RAM、用户 tensor、注册代码及 RTS 参数存储分别核算，不假装属于同一物理池。DFX 的已批准独立预算继续适用。

Kernel_bin、代码表和常驻常量按身份、配置与 context 代际复用；已注册资源不能因为当前没有在飞 run 就透明淘汰。RTS launch 参数按 RTS 合同管理；释放仍需最后使用证明，不以未观察到引用代替无人使用。

### G4. 最后使用者决定复用边界

统一管理的是容量与所有权；不同子区的内容可以有不同寿命。
“每次值不同”不等于“每次分配一整套空间”；地址有效也不等于内容可以覆盖。

- 执行 scratch 在实际串行执行域内复用，按峰值同时存活需求定容；后继有序初始化，
  不要求独立并发执行域共享同一子区。
- Host 提前准备、设备稍后读取的参数和 image，可以由 RTS 保存值副本、写入不同子区，
  或安排在前驱最后读取后覆盖同一子区。值拷贝不会自动深拷贝其中 device 地址所指的内容。
- 上传源保留到复制操作消费完字节；输出 staging、终态、计时和 DFX 保留到最后消费且设备不再引用。
- 按需增长保留旧块和已发布地址；graph 需要的不可变内容也须保留。一次执行结束或 stream sync
  不解除仍可 replay 的 graph 的长期引用，统一释放必须满足拥有者安全关闭条件。

### G5. 设备执行依赖显式有序，host 准备不能依赖尚未执行的工作

资源与依赖安全时允许后继提前入队，利用设备自然排队；host 收尾不应天然阻止后继设备执行。
串行 submit 只描述 host 调用次序，不自动证明不同 stream / endpoint 的执行顺序。
Stream 数量、event / join 形状由后端决定，但必须覆盖所有使用者的初始化和最后使用边界。

Host 准备读取的数据必须已经就绪，准备过程不能等待自己尚未提交的设备工作产生所需值。
就绪性与存储访问冲突必须有明确责任方。Pipeline A 采用的调用方合同及 HBG producer 拒绝，
是本原则的具体应用，见 A 轨 §4，而非新增全局 tensor 依赖跟踪的要求。

### G6. 准备结果完整交付，capture 的固化与更新合同明确

Host 准备产生的、影响设备执行的结果，必须进入可重放任务的参数或受生命周期保护的资源。
Replay 的执行正确性不能依赖再次运行原来的 host prepare。Capture 前准备所需容量，
launch / replay 不申请或扩容底层内存块；设备内部动态分配使用已准备的容量。

区分固定配置、可更新参数，以及参与 host 构图决策的值。仅修改参数地址或数值，不能假定
已生成的任务拓扑和派生内容自动改变。例如 host 按 n=4 生成四个任务，之后将 n 改成 8，
不能只换参数就当作已有八个任务：必须有明确的重新准备 / 任务更新协议，或把决策放到设备执行阶段。

Tensor / scalar 的类型之外，还须定义数据位置、读取时机和是否影响构图。DFX 的设备配置
同样要完整交付；host 采集与文件输出按自身完成合同工作，不能成为每次 replay 中途必经的 host 步骤。
若支持逐次 replay 归属，身份协议不能只复用 capture 时固定的一次 host 编号。

Capture 保存 stream 任务，任务与参数更新需要相应协议；不是任意 host 代码的自动重放。
参见 [CANN capture 接口说明](https://www.hiascend.com/document/detail/zh/canncommercial/83RC1/API/appdevgapi/aclcppdevg_03_1782.html)。
具体平台 / SDK 的支持范围仍须由相应实现验证，不由此原则宣称已经可用。

## 三、完成、诊断与验证

### G7. 完成、设备健康和资源回收分别判断

成功必须有有效且可归属的正面证据；未收到异常或错误字段为零不能单独证明成功。
完成证据缺失、身份不符、格式无效或读回失败不能静默当作成功。
Run 结果、设备健康、资源可回收分别判断，不能把无法归属的后继故障算成前驱的业务失败。

本原则不强制某一种结果区、event 或每次 host finalize 读回流程。
Eager 与 capture 可以使用不同机制，但都须满足所宣称的完成、错误和回收合同。

### G8. 诊断保留归属，结论对应可核查证据

DFX 服务常驻不等于记录可以覆盖。先建立记录身份与 buffer 发布、消费、归还协议，
再取消逐 run 清空和排空；run 完成与采集输出完成的合同须明确，改变保证时必须显式说明。
连续采集和合并输出是可选实施方向，不能把它们自动变成普通路径排队的全量前置。

测量绑定确切代码、实际加载产物、命令和环境，区分冷启动、稳定阶段和不同计时口径。
未启动或跳过不算测试通过 / 失败；减少字节或分配次数不等于降低延迟、显存或碎片。
相关性、共享负载下的波动、放宽超时后的通过，不能直接作为根因证明。

## 四、原则与项目范围

总体原则约束所有后续设计，但每个项目只承接它改变的合同和必要验收。
Pipeline A 必须解决提前入队造成的覆盖、排序、完成及回收问题；不要求先完成统一 allocator、
program / kernel API 分层、全部 capture 能力、A5 mixed launch 或完整 DFX 连续采集。
独立改造只有直接阻止安全提前 launch 的部分，才成为 A 轨前置。

串行 submit 的当前支持范围、两个 slot 的首个里程碑、双流、slot / epoch / event 机制、
DFX 暂时在飞 1、具体块大小及 PR 顺序属于实现选择，不作为永久总体原则。
Init 定预算与旧块保留是已确认策略；init 是否立即分配满额是实现选择。
