program 自然排队 / kernel 接入

前六版把"去掉固定槽位"和一整套新 API、tiling 缓存、ACLGraph 绑成一个交付。 两轮 review 加一份源码核查之后，最有价值的结论是分轨。 v7 替换了三处核心：资源判据、寿命分类、构建读写合同。

基线 748c39fbe · issue #1853 · 全文 .docs/run-pipeline-redesign.md

1为什么必须分轨

simpler_kernel_mode_supported() 返回 0，其后的 kernel 入口是共享 参数校验的占位实现（c_api_shared.cpp:1253）。所以"program 与 kernel 共用设备提交"不能读作"复用一个成熟的 kernel_launch"—— 本分支能工作的只有 program 路径，依赖方向是反的。

2资源判据换掉了

前几版用的是"当且仅当 host 碰它 ⟺ PER_RUN"。撤回——它与 本文档自己的 ledger 矛盾（只读 callable 代码被 host 写过却可共享），而且它不回答何时释放。

判据：后继的准备是否可能覆盖一个仍有使用者的版本；以及最后一个使用者何时结束。
最后使用者包括：device 执行、回拷、状态读取、event wait、captured graph。

这条严格更强：它同时给出分类和释放时机。
推论：Runtime / handshake 要按字段拆——哪些是每次参数、哪些是共享 执行状态、哪些是结果。不能因为整个结构在 prepare 里被写过，就永久规定整份每 run 一份。 但拆字段前保留当前隔离：共享化需要逐字段的读写与复位证明。

5构建的读写合同

v6 写的是"HBG 构图禁读任何 device 内容"。撤回——那会回退 HEAD。真实不变量是： orch 必须在本次 device 执行开始前独立完成。入口 tensor 存放在 device，不等于读它 依赖本次 device 执行。

构建时需要的信息允许？依据

host Scalar、调用前已就绪的 host-backed 控制输入允许—
device Tensor 的地址或不透明引用允许仅记录/传递

本次图内已记录 producer 的区域拒绝 runtime_core.cpp:121 的 require_no_producer 同查 owner_task_id 与 TensorMap 重叠 producer

748c39fbe（HEAD，#2212）加的正是 child-memory 的读取能力：在它之前 residency was mutually exclusive with data-dependent orchestration， 那个互斥是它修的 bug。规模：32 个 orchestration 文件调 get_tensor_data， 21 个调 set_tensor_data。a5 onboard 没有 host-map 路径，那里每次访问 本就是一次 device copy。

"已记录 producer"指图中已登记生产者，不需要等到 device 实际写入——恰恰因为还没 执行，等待本次任务不能产生进展。review 的全面禁读是比现有不变量更强的限制， 记为未来 API 边界提案，需承担 32+21 个 orchestration 的迁移成本。不作为本轮规则。

set_tensor_data 是可观察的构建副作用

6五层串行与跨 run 顺序

多 active 父 run 是正确性门

run N   :  A → B      B 写 X，只在 A 完成后 ready
run N+1 :  C          C 读 X，提交时已 ready

多 active ⇒ ready 队列可给出  A → C → B   ← stream FIFO 忠实执行

无报错、无超时，只是结果错。而且没有机制能恢复：TensorMap 按 (RunId, TensorKey) 隔离（tensormap.h:13）， validate_explicit_deps 对跨 run 显式依赖直接抛 （orchestrator.cpp:1176-1186）。二选一：① 保持父 run 提交顺序（默认） 或 ② 建跨 run 依赖。per-execution 的 event join 替代不了这一层，也不应据此 得出"必须做外部 tensor 的全局跨 run 依赖跟踪"。

7caller stream 顺序与四态

态含义
acceptedhost 队列已接受
staged帧快照已就位——可能仅 VALIDATED_ONLY，尚未 native prepare（worker.py:3262）
enqueued已提交到设备，占据了 caller stream 的顺序位置
completed设备完成

不能把尚未完成构建的 host 请求冒充已占据 caller stream 顺序的位置。 kernel 路径的 runtime_c_api.h:639 明确"返回 0 表示已入队"。

8部分提交没有完整 fence

kernel 已提交event 已记录应判今天
✗✗NotStarted✅
✓✓Partial / Complete✅
✓✗Partial 判成 NotStarted 并立即回滚——设备已持有 kernel

机制：progress = Partial 是在 submit_aicore 返回 0 之后 才赋的（native_run_execution.h:152-160），所以把 aclrtRecordEvent 的错误当作该 callback 的返回值，会被判成"首次提交之前的失败"。

  • kernel 提交与 event 记录分账；Partial 要覆盖 kernel_submitted && !event_recorded
  • 已提交但无 fence 的工作要有不依赖 event 的有界 drain/teardown
  • watchdog 不是替代：AICPU 提交失败后，已排队的 AICore 可能在等它，把回收 event 排在后面不能产生进展
  • 即使证明设备静止，也不自动证明业务未产生副作用。只在可证明未执行或有专门恢复 协议时重试一次，不重新运行 host 编排

event 的引用寿命与失败退出

SDK 明写：销毁 event 前，涉及 aclrtSynchronizeEvent / aclrtStreamWaitEvent 的任务必须已完成（acl_rt.h:1458-1464）。 而 wait 是在 launch 之前入队的： 

N+1:  StreamWaitEvent(my_stream, N_event)   ← 成功，任务已在队列
      rtKernelLaunch(...)                    ← 失败

按 N+1 回滚释放会销毁队列仍引用的 event；等"N+1 自己的 fence"则永不触发。所以 预留 / 提交 / 撤销三态，已提交的引用恰好释放一次（正常 fence 或静默证明）， 且 NotStarted ≠ 没有任何 wait 入队。
跨流排序 event 与用于大 args 回收的 timeline event 职责不同，不能因都叫 event 就混用。

9五个内存所有者

所有者管理方式约束
外部 device Tensor调用方所有simpler 不跟踪不释放，也不该无故复制
host-backed Tensor 的 device staging每次分配 + H2D，留到回拷runtime_maker.cpp:1200-1228，全尺寸
Definition blocksimpler 分配并单独上传:485,510；按 slot 保留，扩容释放旧 device block
runtime / SM image + 执行 heapsimpler 自有 arena:851,875；串行执行时可复用
驻留 callable 与代码跨调用复用callable id 上限 64，且是 host↔AICPU 协议的一部分（callable_protocol.h:31）
本分支没有"整个 HBG 图包随 launch args 交 RTS 管理"的路径。 AICPU launch 传 sizeof(KernelArgs)（device_runner_base.cpp:1542）， AICore launch 参数只是指向 device KernelArgs 的指针（:1778）。
所以 8192 / 2 GiB / 2 MiB / ~2048 / 80 MiB 均不采纳为本分支常量；RTS 大 args 与 timeline 回收标为目标/外部实现。

预算与回收分开。代码证明的是"需要安全回收和压力出口"，不证明需要一套完整的字节 预算系统。当前 retained pool 不会仅因 stream sync 自动释放，必须显式 finalize / 回收 / 淘汰。而前几版的"两阶段预算"是对当前顺序（staging 先于编排）的推导， 不是永久契约——真拆成纯 host build 之后，一个预留点可能就够。
