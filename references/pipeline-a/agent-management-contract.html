01 · 三方工作契约

USER

你：方向和最终决策

确定目标、原则、优先级与授权边界。确认跨支线工作和新架构合同，最终决定 PR 是否合入。

不需要逐轮催进度、整理 Claude 回复，或替 manager 核对“是否真的完成”。

MANAGER

我：组织与验收

读代码校验前提，拆任务与依赖，选择下一项、写 prompt、管理原会话、独立静态评审、跟踪 CI、更新看板。

不把作者自评直接当通过，不自动合并，不另开重复 writer。

CLAUDE

实现者：交付一个 PR

在指定 worktree 和原会话内实施，完成授权验证，用仓内技能提交、发布、处理评审及 CI，返回可核对的结果。

遇到新合同或范围变化，报告事实与选择，不自行扩大任务。

动作当前合同
读代码、调查、静态 review、管理文档manager 可自主进行；代码评审可委派只读 reviewer，实施仍只有一个 owner。
写生产代码、提交修复交原 Claude 实施；manager 写 prompt 和具体评审意见。
commit / push / 开或更新 PR在明确授权的交付任务内用 github-pr / fix-pr。标为“仅本地”的任务不能借用另一任务的发布权限。
测试当前不重跑既有用例或 sweep。可按任务授权设计新 case、反控及必要的定向编译；不把新 case 授权扩成全量测试授权。CI 结果单独读取。
ready 后当前任务停止实现，等待你确认；head、CI 或阻塞反馈变化时重新评估 ready。
确认已合入后自动选择同一已授权支线、边界明确的下一项。保留合入记录，创建下一任务，不续写已合入 PR。
跨支线 / 新架构合同 / merge前两者先请你确认；merge 始终由你决定。

02 · 目标、任务、PR 分三层记录

记录权威内容与用途
Issue + 仓内设计文档问题、整体目标、原则、验收合同。Issue 的早期描述也要对照代码和后续更正；评论不是天然正确的规格。
registry.md任务执行登记：worktree、分支、原 session、进程/exec、权限、当前阶段、head、下一动作。新条目说明它取代哪些旧约定。
manager-workspace.md管理目录、角色边界、恢复方法与通用操作契约。
claude-managed/*.prompt.md每轮发给 Claude 的准确任务和权限；历史 prompt 留存，不因新授权而回写历史。
*.result.json / stderr / review/*.md作者结果和 manager 评审分开保存；评审固定 SHA，验证说明其范围与限制。
路线 HTML面向你的视图：待确认、待决策、任务 DAG、目录与当前动作。依据上面的记录生成或同步，不发明额外事实。

每项任务的最小信息

目标：解决什么问题 / 怎样才算交付
归属：支线 Issue；一个 owner；worktree + branch + original session
范围：要改什么；依赖的合同；本轮不包含什么
依赖：前驱任务 / 共享接口 / 资源冲突；为什么能并行
权限：只读 / 本地实现 / 已授权 PR；测试与外部操作边界
证据：source base、PR head、review head、CI head、测量适用范围
状态：当前阶段；阻塞项；下一动作；最后核对时间
交付后：ready 等你确认；merged 后复核并挑选下一项

03 · 按合同与资源判断并行，按交付物画 DAG

先识别谁消费谁的结果，再检查共享协议、文件和测试资源。文件不同不等于可以独立改；同文件也不必然构成语义依赖。

硬依赖

后项需要前项给出的接口、寿命证明或行为。画箭头，并写清前项输出什么、后项何时能接入。

协同边界

共用 wire layout、owner、初始化或发布协议时，指定一个实施 owner；另一项可先做固定基线的调查或方案。

执行资源

独立代码任务仍可能争用硬件、构建目录或同一分支。代码能并行，不代表硬件 A/B 能并发跑。

这是依赖关系示例，不是实时进度副本。#2254 整项不作为 P4 前置；实际采用的共享区域方案仍须满足 P4 的跨流顺序和寿命要求。

一个格，还是多个格？

  • 能独立验收、独立失败或并行实施的交付物，拆格。例如证据采集、健康策略、生产 drain 接入。
  • 必须共同成立才能安全交付的原子改动，放同格。例如 gate 布局、完整分配和上传长度拆分；program/kernel 两条调用路径列为格内验收项。
  • 一个 PR 交付一个完整功能：持续运行、资源/背压、失败/关闭与真实 API 验收共同成立。不能按容量数字或寿命补丁拆成零碎交付；独立可选能力才另立项。历史跨 PR 交付仍保留证据。

04 · 从委派到合入，再回到目标

Ready = 当前 head 静态评审通过 + 阻塞反馈已处理 + 相关 CI 已完成且结果可接受。

作者说“完成”、本地旧测试全绿、旧 SHA 的 CI、CodeRabbit 限流或未审，都不能替代这些条件。manager 直接核对当前 head；作者仍在等待或尚未返回结果文件，不是额外的 ready 前置。CI 状态须同时显示 head、run 链接、核对时间与剩余检查，不能只写“运行中”。ready 不等于已合入，更不等于允许自动 merge。

review 按 merge-base 到 head 看真实差异，对照目标核查生产路径、失败路径和测试区分能力。rebase 后复核差异及相关上下文；head 改变时旧评审需补核，CI 也必须对应当前提交。无法证明的地方明确保留不确定性。

CI 重试由 manager 按当前用户授权判断，同一失败问题最多重试两次；同样错误出现三次转定位修复，不因换 head 清零。受理不明先核实，禁止重复提交。Ready 必须同时满足当前 head 评审、阻塞意见闭环与相关 CI 完成；较新阻塞可以撤回历史 Ready。路线阶段表、HTML、registry 及状态 JSON 必须同步，已合入与未合入不混记。

05 · 传递可核对的任务，不转发模糊结论

Manager → Claude

给问题、基线、已核实代码证据、具体交付、验收、文件边界、协作 owner 和操作权限。写明是调查、实现还是反馈修复。

“继续优化”“都修一下”不是可验收任务。

Claude → Manager

返回 PR / head / base、修改与原因、验证命令及结果、反控、未解决项、CI 和限制。保留证据路径。

区分“测到了”“代码说明”“推测”；撤回的结论同步到文档和相关 PR。

Manager → 你

ready PR、需要你决定的具体合同、支线进度、下一动作。日常修复和等待由 manager 消化，HTML 随状态变化更新。

问题需带选项与影响，不把原始日志堆给你。

派发前去重：最新 main 与全部 open PR

manager先检查最新main的实际实现，并完整获取所有open PR（含draft）。对可能重叠的工作读取正文、当前diff和负责人：已合入就撤销重复任务，已有PR覆盖就跟进原作者或明确分工。

任务级核查记录绑定prompt和main/open PR快照，派发脚本在真正启动前再次查询；状态变化或缺核查记录时停止派发，先重审。语义判断由manager负责，不能仅凭题目不同排除重叠。原作者开始修改及发布前再核相关PR，避免检查后发生的合入或新PR造成重复。

具体核查步骤与派发记录。这不增加用户审批，也不重启现有writer。

上下文门禁：每次发送 prompt 前

读取原会话最近一次请求的输入与缓存 token，除以实际模型容量；不把累计用量当上下文。超过 80%：等本轮结束 → 同会话 /compact → 验证压缩记录与压缩后用量 → 再发任务。检查失败或压缩失败时保留待办，不盲发、不另开 writer。保留目标、授权、head、未决反馈和证据路径；所有任务与反馈通过 manager 的 dispatch_claude.py 派发。

计算口径参照 Claude 官方上下文用量说明；本机通过原会话 transcript 和结果元数据读取，压缩后先使用 compact_boundary.postTokens。检查证据在 context-checks.jsonl。

会话和目录寿命

  • manager 在 pipeline-a-manager 维护任务、评审、HTML；实现留在原 worktree。
  • 恢复前检查该会话或 worktree 是否已有 writer；使用原 --worktree … --resume …，不同时恢复第二个 writer。
  • 进程在跑且结果 JSON 为空不代表卡死；结合进程和最近有效进度判断。历史 session ID 也不证明进程仍在运行。
  • 反馈等待本轮结束后再恢复原会话；需要即时纠偏时使用可用消息渠道或明确中断，不并行启动同一实现。
  • 合入后，原会话可在干净的新任务分支继续；不 amend 已合入 PR，不删除别的任务的 stash、文件或分支。

07 · 有续办机制，也有停止条件

当前通过本机 cron → codex queue → 原 manager 线程 每 10 分钟触发续办。enabled 控制启停，pending 防重复排入，flock 防脚本并发；每轮先清除本轮 pending，再核对登记表和原会话。

  1. 读取最新用户授权和登记，检查是否有合入、head 变化或需要处理的结果。
  2. 推进可执行工作：静态评审、给原 Claude 具体反馈、确认发布和 CI、安排已合入支线的下一项。
  3. 同步 ready 数量、DAG、目录状态和核对时间；保留尚未完成的事项。
  4. 所有在途 PR 均 ready 等你确认、目标全部交付，或所有有效工作都被真实用户决策阻塞时，停止当前定时续办；后续合入或新授权触发恢复。

这是本机 cron 与已安装 CLI 的组合，依赖主机和会话服务可用，不保证离线执行。停用时只移除该 manager 的 enabled 和带指定 tag 的 cron 行，保留其他用户任务。计时器不是工作成果；每轮必须推进一个可推进的动作，或记录准确等待条件。

08 · 已确认的合同变更

2026-09-19：合入后自动续做。

你已确认：“按此规则自动续做。”适用同一已授权支线中、边界明确的下一项；跨支线或涉及新架构合同，仍先确认。这取代早先“每个目录一个 ready PR 后不开始下一项”的长期停止规则；ready 期间等待用户确认的规则继续保留。

未授权的本地任务不自动变成可发布任务。当前仅本地的内存清点仍保留其权限标记，不能通过调整状态表暗中升级。

工作线、目录和会话一一对应

同一工作线复用原 worktree 和原 Claude 会话；独立的新工作线新建 worktree 与会话，不能因为某会话空闲就跨线派发。已完成会话保留历史并置闲。恢复旧会话先查登记表、真实进程与上下文；超过 80% 先压缩同一会话并验证。

设计可并行不等于生产集成可以跳过依赖。DAG 分别标明当前设计、实现授权和集成前置；共享文件有明确负责人，交接接口后再集成，避免两个 writer 改同一目录。新会话首次派发登记空上下文，后续使用统一上下文门禁。
