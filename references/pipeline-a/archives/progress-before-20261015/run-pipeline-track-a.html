比较场景：同一个本地 L3 / A3 HBG program endpoint，A 写入调用方通过 child/context 分配接口取得的设备 tensor y，B 读取 y，再把设备结果交给 C；地址与布局预先已知，无诊断和复杂通信。

这份 PR 没有删除 slot。它在现有固定容量执行框架内补齐 DEVICE 输入的引用与访问保护。“可以持续补队”指槽位安全退休后反复复用，不代表 A、B 占用时 C 也能无限继续提交。

这里保留的是谁的内存？

是调用方通过 Worker.malloc → device_malloc_ctx 获得并传入的 child-device 分配。A 把结果写进它，B 继续使用同一地址；PR只登记借用与生产者、阻止过早释放，不另复制一份中间tensor。HOST参数自行H2D得到的 RetainedTempBump 副本不参与这套借用表；任意外部分配也不自动纳入保护。

新增加的是怎样的保护？

数据：一直留在设备

A → device y → B → device z → C

新能力不是“第一次可以用 DEVICE tensor”，而是取得可验证的借用后，B 可在 A 尚未完成时准备并加入设备队列。内容稍后由 A 产生，FIFO 保证 B 按顺序消费。

寿命：最后消费者结束才允许释放

每个 run 对所引用设备内存登记借用。即使 A 已结束，只要 B 仍可能使用 y，就不能释放 y。若停止或 finalize 无法证明完成，保留相关引用并拒绝不安全的释放。

host 构图若真的需要读取 y 的内容，仍要等待生产者；不能凭地址已知就读取未完成结果。

DFX · #2427 修正连续采集文件中的 run 归属

已合入

负责人：temporal 原 Claude

让每次运行的诊断文件拿到本次主机提交、上传记录及计数，避免漏记或串到上一次运行。

查看这个 PR 解决什么问题、怎么改、影响范围

原来的问题：后台采集需要先把一次运行的记录封存，再交后台写文件。原代码却先封存、后更新本次主机记录：第一次运行可能没有主机记录，第二次文件可能装着第一次的记录，时间线与任务归属因此错位。

举例：N 有 10 条主机记录，N+1 有 3 条。修复后，两份诊断文件分别保留自己的 10 条和 3 条；如果 N+1 没产生主机记录，它的文件也不会沿用 N 的 10 条。

具体改动：

  • 先更新，再封存：板端与仿真共用同一收尾顺序，把本 run 的主机记录写入采集器，再复制到该 run 独立持有的记录中；仿真的运行时扩展信息也按此顺序处理。

04

两条流，一个运行边界

一个 program run 的 AICore workers 与 AICPU scheduler 需要协作。每条 stream 内有 FIFO，但两条 stream 之间必须显式建立前后运行的边界。

已交付 A5 HBG #2481：AICPU 流在 A 的 kernel 后等待 A_core_end，再记录 A_whole；AICore 流提交 B 前等待 A_whole。AICPU 侧的 A→B 顺序由同流 FIFO 保证。等待消费证明用于资源退休，与 B 完成分开；该问题已在#2481交付前修正并验收；后续#2491已支持A5 TMR。A3 TMR已由#2560交付；当前推进四后端取消固定资源上限。当前交付与阻塞。

完成：只等本 run

poll / drain 查询或等待该 run 的两个 event。常规完成路径不再用整条 stream 的 synchronize，否则会把已经排在后面的 run 一起等完。

历史示意的排序关系

core(N+1) waits cpu(N)
cpu(N+1) waits core(N)

各自本流的先后由 FIFO 保障，交叉 event 补齐另一半。

异常恢复仍可需要 stream / 设备层面的静止证明。常规 per-run 完成判据与异常收敛机制，承担不同职责。

05

三种顺序，要分别守住

设备执行有序、父 run 提交有序、host 访问输入有序，是三个不同问题。底层 stream 的自然队列只能直接解决第一个。

HBG 构图必须能在本次设备执行前完成

可以读取已经就绪的入口 tensor，包括 device 上的入口数据。一旦本次图内已存在 producer，即使底层存储原本是入口 tensor，也必须拒绝在 orch 中读取其结果。

本次图内依赖：已有边界

require_no_producer 检查 owner 与重叠 writer。本次 kernel 写出的值不能成为本次 host orch 的前提；device predicate 可留到执行时求值。

跨 run host 访问：调用方负责

调用方保证 get 所读入口在 prepare 前就绪，set 所写存储没有冲突使用者。若依赖前次运行，先显式等待完成及必要回拷，再提交本次。独立或共享只读的就绪入口继续提前构图。

首版采用调用方合同：不新增跨 run 读写记录、自动冲突检测或相关前驱等待，也不承诺违约一定报错。合同覆盖别名、切片和 host staging 的原始存储；device staging 地址不同不能代替 host 访问同步。仅在设备 kernel 中访问的共享数据，仍可由正确的提交顺序与双流 join 排序。

同一个 callable 的 build 继续串行

SO 内 g_current_runtime 是普通全局。保持同 callable 的跨 run 构图串行，保留一次构图内部的 recorder 并行，并允许构图与前驱设备执行重叠。

Python 直连 copy / free 等 host 副作用继续遵守相关完成等待；不同 endpoint 的 stream 不形成相互顺序。新建独立资源不应被一概认定为依赖前驱。

06

入过队，就要对寿命负责

多在飞后，某个 run 失败不意味着它后面的任务可以撤回。先停止危险的新准入，再证明队列不再访问相关资源，最后进入终态与回收。

kernel_submittedevent_recorded必须表达的语义
否否kernel 尚未开始提交；但可能已有 StreamWaitEvent 入队，仍需管理引用。
是是本流有完成 fence；整次 launch 是否完整，还取决于另一条流。
是否Partial：设备已持有 kernel，不能按 NotStarted 直接回滚。

这是引入 per-run event 时必须覆盖的新失败组合。这是原设计针对新增 event 的风险模型；#2419 已交付有限排队实现，当前缺陷结论须依据实际 head 与 #2429 诊断，不能把旧设计缺口当作现存缺陷。

业务结果、执行静止和 pair 健康须分别判断。下述是设计约束，当前实现范围与遗留问题由 #2429 按精确 head 验收。空流必须没有任何命令入队；若只有 wait，也不能提前释放它持有的 event。

event 引用的三步记账

1 · 预留enqueue wait 之前持有前驱 event 引用
2 · 提交 / 撤销wait 成功则提交；失败则撤销预留
3 · 恰好释放一次逐流确认相关 wait 完成或静止
最后才销毁所有 wait / sync 使用者都已结束
不能用 watchdog 代替回收协议。例如 AICore 已入队而 AICPU 提交失败，前者可能一直等待后者；排在后面的普通 event 本身不保证进展。必须有不依赖缺失 fence 的有界恢复路径。
07

取消固定槽位，以真实资源承接背压

目标不保留固定两槽准入上限。输入、参数版本与资源预算允许时，N+2 可以提前准备和提交，不必仅因 N 尚未 finalize 而等待槽位。共享可变 device workspace 仍按执行顺序串行使用。

取消固定槽位不等于无限积压。每次参数、结果和 event 仍须保留到最后使用者结束；提交队列压力与资源预算负责背压。当前代码仍有两槽结构，这是迁移对象，不是最终合同。
