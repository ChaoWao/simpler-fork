01 / OWNER MAP

先把主机内存与设备内存分开

Host · 主机侧

用户数据HOST tensor、框架对象；由用户／框架拥有。
simpler 准备数据构图对象、image 与参数打包暂存；launch 时向 RTS 提供参数内容。

Device · 设备侧

WorkspaceManager 覆盖的四类tensor 暂存副本 + GM heap + GM SM + runtime_pool。独立区域、独立归属，统一记账。
RTS 参数载体调用描述与 HBG 图定义随 launch 复制；并不自动替代 tensor 数值数据的 H2D。
其他 owner 持有的空间用户 DEVICE tensor、代码与函数表、执行状态、结果、DFX 池、通信与驱动资源。

“统一”首先是统一所有权与回收规则；不是把所有内容塞进一个 malloc，也不是所有内存都由 WorkspaceManager 分配。

03 / LIFETIME

一次 run 结束，不等于这块内存该 free

两层寿命：context 持有“当前可复用容量”；run 持有“这次使用的引用”。run 引用可以先结束，容量继续留在 context 中供下一次使用。

点选阶段：看同一块 workspace 为什么仍然存在

run 使用引用

底层容量

这是当前规则的解释示例，不是设备时间线或性能测量。不同 runtime 不要求所有四区都使用同一 bank，也不要求每次调用各 malloc 一份。

WorkspaceManager 如何确认引用可以退休？

设备事实已证明设备工作完成，或者这次调用从未向设备提交。
主机消费者回拷已返回，不再有这个 run 的 copyback 读取者。
绑定事实相关 bindings 已成功释放。只看到返回码不够。
引用退休三项事实满足，放掉该 run 的引用；之后再判断当前容量保留还是旧代回收。

精确退休条件 ↗ · run 事实记录 ↗

若 run context 消失，但最后消费者是否结束无法证明：关联块进入隔离，不再拿去复用或当作已释放。设备故障后的“记了一条日志”或普通返回码，不能代替停止与归还的证明。

slot / bank 在这里表示什么？

当前代码仍用有限的资源位置组织参数、暂存与结果；bank 指一组 arena 的存储归属。它们不是独立 stream，也不代表每个历史 run 都永久保留一套内存。旧引用按 run 身份登记，安全退休后移除；资源位置之后可以再次使用。

设备串行只保证设备命令按顺序执行。host 可能正在提前准备后继，因此地址还有效和原内容还没被覆盖必须分别保证。只有现有准入、资源隔离与初始化顺序证明安全的组合，才允许提前准备或 launch。

04 / GROWTH & FAILURE

为什么扩容，以及排队时怎么保全旧块

输入形状、tensor 总字节数、编排容量或 runtime 布局改变，下一次请求可能超过保留容量。初始化／已有容量不是每个程序都按全局最大值预分配。

情形当前处理内存含义
容量足够复用已有容量，并为此次 run 登记使用；内容复用仍受排序／资源许可约束。没有本次 malloc，不等于没有本次消费者。
容量不够先准备替代块。arena 计划成功后才发布新地址；失败保留旧计划。retained_temp 同样先取得新块再替换当前指向。扩容时新旧块同时存在；用户看到的旧地址不会因替代块刚申请成功就被释放。
旧代仍被使用即使新代已发布，也保留旧代；等旧代最后消费者结束，再在安全回收路径处理。正常代际保留；不是复制所有历史任务，更不是无限历史地址表。
旧代已无人使用满足无引用、无隔离、释放状态可信及 host 映射处理等条件后，允许回收旧代。当前有效 backing 即使空闲，仍可保留；旧代才进入淘汰集合。
设备 malloc 失败／可选预算拒绝本次 run 报错，原地址、容量和已发布计划保全。失败保全不保证新 run 仍能成功。
停止未知／unmap 或 free 失败保留隔离／释放未确认记录，限制危险复用或新块发布，按原关闭路径报告。不把“尝试 free”写成“已归还”。不同失败类别有不同终态处理，不能承诺总能原地恢复。
数字示例，非实测：原块 8 MiB，下一次需要 12 MiB。若需新块且旧块仍被引用，两者同时持有至少 20 MiB 的申请容量；还没计算其他区域、对齐、RTS 和驱动开销。可选预算也要考虑保留旧代的峰值，不能只按下一次的 12 MiB 来理解。

05 / L2 & L3

L2 与 L3：安全机制相同，持有进程不同

同进程 L2本地 L3
谁持有设备工作区当前进程内的 ChipWorker／device context。各 chip 子进程内的 ChipWorker／device context，不是父进程持有一个全局设备大池。
申请节奏在初始化／准备阶段取得已知需求，重复调用容量够则复用；未知的大需求仍可能引起增长。子进程按实际需求分配和增长，容量够同样复用；不是每个 run 都 malloc/free。
默认机制a2a3/a5 onboard program 默认管理四区。内部兼容参数 manage_workspace 不再决定是否采用安全机制。
预算入口Worker 的 workspace_budget_bytes 可选；不设置就不施加这项额度。当前 Worker 层级入口不支持这个预算配置；不做“两个设备各分一半”的总额均分。
关闭边界本进程可以查询 live workspace 消费者并拒绝过早拆除。子进程执行自身收尾；本轮没有增加父进程询问所有子进程新鲜账本的关闭回传协议，不能套用 L2 的同进程证明。

L2 预算与关闭检查 ↗ · L3 显式预算拒绝 ↗

预算限定的是四区已持有的 backing 字节，包含仍保留的旧代。它不是 HBM 总额，也不是预分配承诺。DFX 主机保留额度、代码池、RTS 参数、用户 tensor 和通信内存各自另算。

06 / COMPLETION & LIMITS

目前完成到哪里，哪些还没有承诺

这批工作已经完成

  • 四类 workspace 默认统一登记与管理；L2、本地 L3 以及底层 onboard program 初始化机制一致。
  • 容量够就复用，增长失败保全旧计划；引用与实际消费者事实挂钩。
  • 被替换旧代延迟回收；当前 backing 可留给后续调用。
  • HBG 图定义随 KernelArgs 交给 RTS；可变执行状态保持独立 owner。
  • 用户 tensor 所有权不被接管；已有函数地址表按注册资源复用。

边界仍然存在

  • 不是全设备、全进程的统一内存池；多类资源明确在四区账本之外。
  • 当前只报告部分覆盖，不能凭一个 workspace 数字解释全部 OOM。
  • 没有新增 remote／MPI 的关闭回传与进程内故障恢复保证。
  • sim、kernel 模式不能直接套用 onboard program 的全部管理结论。
  • capture／replay 尚未接入；没有本轮实测峰值或延迟收益承诺。

现在的结论：本轮已批准的内存改造与收尾审计完成。后续只有发现具体生命周期缺陷、测量到明确成本，或新增模式获得授权时，再选择相应任务。

仅为补一个更大的内存统计数字而修改公共报告接口，当前未立项；不是用户待审批事项。即使暴露本分配器 committed_bytes，也仍不等于整卡总占用。
