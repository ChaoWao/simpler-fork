# 内存归一化首步怎么工作

状态：用户阅读工作过程解释后已明确批准本首步实现并交付一个 PR。2026-09-23T07:54:17.894796+00:00

## 一个 owner，四类使用者

每个受支持的 device runtime context 有一个 workspace 管理器。它实际拥有底层 device 分配和额度账本；retained_temp、gm_heap、gm_sm、runtime_pool 只持相应区域的使用权，不再各自独立决定释放。

- retained_temp：host 输入/输出在 device 上的临时存放区，涉及上传、执行和回拷。
- gm_heap：计算中间结果等使用的 GM heap。
- gm_sm：运行时共享状态的 GM 区域，不是片上共享存储。
- runtime_pool：预制 runtime/调度等对象布局的 arena。

统一的是预算和所有权；首步保持独立块，不把四类强行拼成一个超大连续分配。也不接管外部框架 tensor、代码池、DFX、RTS/provider 的内存。

## 正常一次运行

1. init 确定这四类区域的有限预算，启用后不自动提高。
2. prepare 算出本次区域大小，向管理器请求。已有块够大、布局兼容且内容可以安全复用时用旧块。
3. prepare 获得地址及使用权记录，记录所属 run/slot/context 世代。现有上传和 launch 使用这些地址。
4. 各使用者完成后归还各自引用。输入在设备最后读取后可归还；输出/INOUT 还要等所需回拷结束；runtime 状态要等所有设备使用结束。
5. 没有剩余引用才允许覆盖复用。归还给管理器不等于每 run 都调用 rtFree；池内留作复用的实际块仍计入额度。

地址稳定与内容保留分别判断：地址没释放，也不能提前覆盖仍会读取的内容。

## 扩容例子

只看一个区域，忽略对齐和其他已经计入的区域：旧块 A 为3 MiB，旧消费者仍可能读取它；新准备需要5 MiB。

预算容得下8 MiB且现有准入允许准备时，另分配 B=5 MiB。旧消费者继续拿 A，新计划拿 B，A 保留到最后使用者结束。扩容是新计划取得更大的块，不是把 A 搬到 B 后马上释放 A，也不自动把旧数据复制成新输入。

若预算只能容纳7 MiB，或者实际设备申请 B 失败，则本次准备失败；A 的地址、容量和已发布计划保持不变。不能为了让新请求成功而先释放 A。此例不放宽现有 bank/slot 准入，不允许当前调度禁止的并发准备。

所有旧代、新块、暂存块和空闲池块都按实际底层分配计入预算；不是只计当前 run 所需大小。

## 谁来保证失败不会漏账

先预留 host 所有权节点和 allocator 跟踪节点，再在持锁期间分配 device 块，成功后以不会再次分配 host 内存的步骤提交记录。多区域计划全成功才发布；中途失败回滚暂存，释放失败的块保留 owner 与计费。

普通完成并不自动证明安全。关闭时，有仍可排干的使用者就阻止过早清理；查询失败也不能当作没有使用者。无法证明最后使用者已经结束的块隔离，禁止单独释放或解除映射。沿用已有 reset 策略，不承诺 reset 或新建 Worker 能找回未知字节。

## capture 为什么能用这个方向

未来图 G 捕获了 A，就让图也持有 A 的引用。一次 replay 完成只结束本次执行引用，不释放图引用；G 仍可 replay 时 A 继续有效。销毁图且所有 replay/其他消费者结束后才回收。捕获前准备容量，capture/launch/replay 不扩底层块。

这需要实际的图创建、克隆/更新、销毁与 replay 接线。首步只实现同进程 L2 program eager 的共同底座，没有实现这些 capture API，也没有父子进程关闭协议。因此不能把首步验收写成完整 eager/capture 统一池完成。
