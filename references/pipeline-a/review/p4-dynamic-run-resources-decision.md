# 普通异步：解除固定 2/3 套资源限制

状态：用户已于2026-10-14批准完整合同，进入实施派发。一个 PR 交付完整功能；尚无新代码或运行验收结论。

## 要解决什么

当前四种 program 后端已有有限深度提前入队，但请求身份、mailbox 帧、native 状态和执行存储仍绑定固定槽号。不能通过仅把 3 改成 4 获得可配置、持续运行的异步模型。

目标是让本地 L3 的 A3/A5 × HBG/TMR 都能按配置和实际资源持续提交超过三个 run。设备仍串行执行，提前提交只减少等待下一次提交造成的空隙，不承诺性能收益。

## 一次提交怎么走

1. `Worker.submit` 为请求分配独立 run 身份，放入已有逻辑 FIFO。`pending_run_depth` 继续限制排队请求；满了等待完成唤醒。
2. 父进程借一帧传 callable/config/参数和身份。子进程复制完参数后归还传输帧；该帧可以传后面的请求，不必等当前设备执行结束。
3. 每个设备端点按 `pipeline_depth` 获准持有执行资源。优先复用空闲存储；不足时按需构造和分配，到达配置上限则背压。设备内存分配失败使本次未启动请求失败，保全已有资源。可选 workspace 预算保持可选，不要求预设全设备上限。
4. 已准备好的 FIFO 前缀按 `launch_depth` 提前进入设备队列。每个 run 有自己的参数、完成事件、结果及错误记录；设备执行顺序不变。TMR 尺寸不兼容时沿用等待/串行准备规则，不能因为还有空闲资源就重建前驱正在使用的共享区。
5. 设备完成、输出拷回、绑定引用与调用方借用全部结束后，执行存储才可复用。完成/错误结果复制进调用方句柄后，传输状态记录才可回收。旧句柄反复 wait/result 仍得到同一结果；不保存用户 tensor 的历史副本。

## 一个具体例子

`pipeline_depth=8, launch_depth=4, pending_run_depth=64`：最多持有八套执行存储，其中最多四个 run 已提交给设备，其余可准备待发；后续请求留在主机队列。A 安全退休后其存储用于后续请求，连续运行64次，不会因槽号用完而停止，也不为每次请求永久追加存储。

8 和 4 是本次配置，不是新硬编码上限。默认 `pipeline_depth=2`、`launch_depth=1` 保持；实际深度受可分配内存、传输尺寸校验和 runtime 兼容条件约束。单/多设备按各端点管理，DEVICE 地址仍属于其原设备，不自动推断跨设备可达或数据依赖。

## 三种容量分开

| 对象 | 数量/寿命 | 为什么独立 |
|---|---|---|
| 传参数的帧 | 每端点默认2帧，每帧64 KiB；子进程接收完成即归还 | 不需要每个在途run占一整帧 |
| run 状态记录 | 每端点 `获准执行资源数 + 传输帧数`，约336 B/项；终态取走后归还 | 保存独立身份、接受状态和完整错误文本 |
| 执行资源 | 按需创建，最多配置的pipeline_depth；最后消费者结束后复用 | 不再由固定槽数组决定可排队数量 |

DFX 的设备采集银行和主机待写文件额度继续独立。已有允许提前入队的诊断路径按 run 身份借还采集银行；银行满则等待原有退休进度，不能静默关闭诊断。当前三个采集银行不是普通执行资源的新上限，本 PR 不扩大诊断支持范围。

## 失败和关闭

同一 run 的 poll/wait/finalize 串行进入 runtime，finalize 独占保留，等待中的调用醒来后重新查身份。一次成功完成的 wait 不重复执行，错误不会被后续清理覆盖；沿用现有 finalize 错误优先于 wait 错误的规则。

有确认的完成/释放证据才复用资源。执行是否停止不明、清理中抛异常或状态损坏时隔离资源，停止该 lane 的新提交并保留调用方借用，沿现有 close/abandon 路径报错；不加入自动恢复或新的 reset。正常 close 排干未等待请求。销毁 context 不等于设备资源已经安全释放。

## 成本与边界

- 配置更大的在途深度会同时持有更多参数、事件及设备存储；按需分配不代表内存无上限。故障隔离可能保留资源到既有关闭/放弃边界。
- 每端点请求帧约128 KiB，加上述状态表及控制帧；默认状态表约1.3 KiB，八套执行资源时约3.3 KiB。精确大小按编译布局校验。每个活跃 run 增加映射记录和操作租约、锁/唤醒管理。
- 不承诺设备内存减少或延迟/吞吐收益。所有共享布局生产者和消费者须一致重建；不新增版本号或版本协商。
- 本 PR 覆盖本地 L3 普通 program、四后端、单/多端点、HOST/DEVICE 参数及 sim 对应行为。capture、remote/MPI、通信 collective、kernel 模式和跨设备地址访问不开放。

## 一个 PR 的完成条件

四后端均通过真实 Worker.submit 验证：配置超过3、同一时刻至少4个独立run已提交且被接受、64次持续补队、默认行为、尺寸变化回退、HOST/DEVICE寿命、晚读结果、故障与close。确定性的 native 注入用例验证并发等待/清理、错误优先级、陈旧身份及异常隔离；Python 日志解析用例不能替代 native 协议验证。
