# P4：三套 run 资源与连续设备排队 — 用户已批准

基线410502f7b；原作者第4次修订及manager静态核对。用户已批准实现并交付一个完整PR。

## 要改变的行为

今天 `pending_run_depth=4` 可以让主机提前构图，但 native 只有两套资源：A执行、B已提交，C与D只在主机等待。首步增加显式 `pipeline_depth=3, launch_depth=3`：A还未完成时，B、C均已被RTS接受；设备依然按A→B→C完整算子串行。A安全退休后，该套资源可承接D，持续补队。

这不是消除所有容量限制：本PR把实现上限从2提升到3，并把准入、实际资源和退休条件对齐；更一般的动态队列仍是后续范围。不承诺性能收益。

## 公共配置与范围

- 新增 `Worker(pipeline_depth=N)` 请求 native 资源套数，首步N限1–3，默认请求2；原 `launch_depth` 默认1保持。显式请求不得静默降级，不能支持时初始化失败并报告请求值与实际值。
- 只有本地L3、一个endpoint、A3/a2a3 onboard HBG program、单任务run可用3。其他runtime、A5、sim、kernel、remote/MPI、L4或多endpoint不新增第三套能力。
- 父进程通过既有fork参数传请求，子进程在native初始化/预热前配置资源，再发布实际容量；父进程用返回容量建立准入。parent READY之后不得反过来重配已预热的native资源。
- 保留逻辑stream串行、诊断独占、DEVICE输入与host读取保护。用户device_malloc释放权不变；不推导tensor依赖、不开放capture。

## 每套资源及何时复用

每个活跃run独立持有参数、arena bank、图定义、调度状态、host staging/mirror、结果区及完成事件。当前内容不能被后续run覆盖。

只有该run设备已停止访问（或证明从未提交）、结果已读取、回拷调用已返回、绑定释放成功、调用方buffer借用结束、后继对完成事件的等待引用已消费并释放，才归还这套资源。回拷返回错误仍使run失败，但若它已返回且借用成功释放，不单凭结果错误阻止安全退休。

L3尚未启用WorkspaceManager时，上述证明由每套run的独立状态持有，不依赖不存在的workspace账本；若某上下文已启用管理器，其块引用另需满足对应退休条件。L3内存管理现已单独批准，由memory作者实施；本PR不代写该支线，合入整合时核对管理启用后的引用与容量。

部分提交失败、无法证明设备停止或未释放的event引用，不准靠清空host记录复用。保持原错误、停止受影响准入，依现有排干/reset实际结果处理；不承诺失败后都能干净关闭。

## 代价与构建边界

当前mailbox和部分账本按编译期上限布局，上限2→3会让每endpoint mailbox由192 KiB增加到256 KiB，其他按槽数组也增加一项，即使未启用第三套也有这部分静态代价。mailbox版本随布局更新，相关组件需一致重建。

显式第三套在初始化预热或后续首次prepare时按实际布局准备，可能增加arena、图、调度状态、参数及结果存储；镜像在大配置下可能达数十MiB。各套容量保持高水位直到context finalize。更多event、引用与状态判断也有开销。套数限制不是字节预算，不引入强制额度或设备均分。

## 验收

必须通过真实 `Worker.submit`：A执行时B/C均已被RTS接受，设备边界保持顺序且不重叠，各run结果正确；A所有消费者结束后D才能取得其资源，16次连续调用能持续补队。另验证默认仍两套、诊断串行、明确不支持范围拒绝、部分提交与event失败不提前复用。仅新增未执行case首跑；不重跑既有测试或CI。manager审查精确head、反馈与CI后交用户合入，不自动merge。
