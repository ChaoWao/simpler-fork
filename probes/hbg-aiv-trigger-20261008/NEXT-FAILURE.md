# 下次 AIV UB 故障：先封存，再重放

状态：用户已恢复调查；本轮两次完整重放未复现，尚无根因或修复。最新结果及可用的 callable 上传探针见 [重放报告](../hbg-aiv-same-conditions-20261009/REPORT.md)。

## 目标与边界

下一次真实测试碰到 `VEC instruction error: the ub address out of bounds` 时，把它变成一份可重放输入包。相同代码、二进制、输入、运行顺序、设备与超时配置是重放的基础，不保证能恢复指令缓存、设备寄存器或线程时序。本次 warm sweep 通过，证明不能只保存失败 nodeid 后单跑它。

这份流程和脚本只在本地，**尚未接入 CI 自动上传，也不声称已经捕获运行时加载地址**。

## 正常测试开始前

不为这项调查额外跑 sweep；在下一次本来就要跑的测试中：

1. 所有硬件命令通过 task-submit。创建独立 ASCEND_PROCESS_LOG_PATH，保存完整 pytest stdout/stderr、命令与退出码。
2. 保存 commit、dirty diff、未跟踪源码、PTO pin、运行库及 callable 二进制；固定 device 列表、runtime、timeout 配置、实际输入/随机种子。种子不能替代已经生成的输入。
3. 外部占用采集器从入队前启动，保留时间戳、队列分配、NPU PID 与父进程链。查询权限失败必须记录；必要时通过不申请设备的 task-submit 重试只读 npu-smi 查询。不要在已持锁的任务里再申请相同设备。
4. 记录实际各子进程的启动/结束顺序、PID、设备、nodeid、命令和相关配置。仅保存 pytest 收集顺序不够；跳过项和完成后补位都会改变执行序列。
5. CI 必须在失败清理/机器回收前上传这些文件；控制台最后 40 行不够。

已有 launch.py 可为既定测试收集日志、运行库 hash 与占用，但**它的外层退出码不代表测试成功**，必须读取 result.json.rc 与 ub_bounds_faults。它未自动归档二进制和输入，也未完整记录加载地址，不能当成已经齐备的 CI 现场包。

## 故障发生后，优先顺序

1. 先保留原始 plog、device log、host log、控制台和占用记录。记录故障 PID、chip/die、PC、kernel/task id，以及超时之前的原始错误。
2. 在 rebuild、清 cache、删 worktree 或再次启动测试之前封存构建产物。允许既有错误处理正常退出；不要为了留现场阻止驱动恢复，也不要自行 reset 其他用户的卡。
3. 用下面的本地脚本复制 scene 目录、build/lib、build/cache/kernels，生成文件大小和 SHA256 清单。输出必须是全新目录：

```bash
python3 "$PROBE/freeze_scene.py" \
  --work "$WORKTREE" --scene "$FAILED_RUN" --out "$ARCHIVE"
```

PROBE 为本文件所在目录。脚本不访问 NPU、不重建、不重跑；会拒绝覆盖旧包。archive.json 的 complete 只表示该脚本定义的文件集合复制成功，不表示设备现场完整。发现复制期间文件变化或缺失会失败；应保留不完整包及错误记录。

另行复制：实际输入、测试输出中的编译中间产物/符号、未跟踪源码，以及不在 scene 目录下的日志。不要保存整份环境变量，避免混入凭据。正在变动的日志不能视作原子快照，待进程退出后再封存最终版本。

4. 核对设备上的实际 PID 与 task-submit 所有者。锁不排除未使用 task-submit 的进程；事后空进程表也不排除故障时挤占。

## 现场重放策略（恢复调查后执行）

- 先重放原始完整命令和原始产物，保持设备与超时设置；不先提高 timeout，不先重编译。
- 若仍持有原 reservation，可在隔离测试正常结束且设备可用后，用同一 reservation 重放；若已释放，重新经 task-submit 申请，并明确记录中间有无其他任务。不能把后来重新申请的卡称为连续保留的现场。
- 完整重放红了，再缩短故障前的执行前缀。完整通过、单例通过仍属于未分类，不能据此判定已修复。
- 如硬件状态必须重置后才能继续，明确把它作为条件变化记录。软件归档无法恢复重置前寄存器或缓存。

## 仍缺的关键能力：故障 PC 对应哪份实际上传代码

需要在 callable 上传边界记录 PID/device、device base、size、内容 hash，并保留匹配二进制、符号/反汇编及 kernel id；记录卸载/复用时间，避免同一地址后来被另一份代码覆盖后误配。先验证每个子进程都覆盖，再依赖这项数据。

目前 copy_trace.so 只抓到一个 PID 的 15 次小 H2D，未覆盖旧故障 PC；不能依靠它完成归因。后续若需补采集，应作为明确的诊断改动，经正常测试验证，不把未验证的 LD_PRELOAD 探针默认塞入 CI。

最有价值的交付是“同一输入包能再次触发相同 PC/错误签名”；在那之前，只能称现场包，不能称稳定复现包。
