4. 当前调用怎么下来

  1. Worker.init：拥有设备的环境

    direct L2 Worker 创建 _ChipWorker，经共同 _initialize_chip_runtime 调用 native init → C++ ChipWorker → simpler_init。L3+ 的 chip child 也直接构造 native；两路共用日志、binary paths 与 options 初始化。

  2. Worker.submit：接受统一 TaskArgs

    复制/验证描述符、tag、transfer 和 scalar；DEVICE 参数查授权与 source use。ImportRegistry 解析本地 backing，materialize_task_args 形成 ChipStorageTaskArgs。描述符快照不等于自动复制所有 tensor 内容。

  3. ChipRunLane.submit：共同准入和寿命

    direct L2 走 _submit_chip_run_direct。lane 根据资源、前驱和能力决定准备/入队，不由 Python 提交次数自行推导 device 队列容量。

  4. simpler_prepare_run：保存本次确定结果

    host RuntimeHandle 指向 address-stable NativeRunContext；bind、publish_run_image_impl、输入处理与 runner prepare。在当前 eager 实现中，metadata 发布仍发生在 prepare，并使用同步复制；host prepare 并非“无任何 device 写入”。

  5. launch：KernelLaunch 与设备顺序

    普通 launch 或带前驱的 joined launch；AICPU/AICore 的协议与资源保护在 platform 层。Native launch、父 run 接受和 device 完成不是同一个时刻。

  6. RunHandle.wait：完成和退休

    native wait/drain/finalize 处理结果校验、所需 copy-back、DFX、资源；Python finalization 再释放 source uses/handle keepalive。不能只凭一次 launch 返回就释放 Buffer。#2580/#2581 已交付可重试的 context 拒绝保护；#2584 已将公开操作前置校验收口到共同 lease。

  1. Worker.submit：父级 Python 编排

    Worker(level≥3) 经 _submit_l3_locked → _Orchestrator._begin_run，调用用户 f(orch,args,cfg)。

  2. Orchestrator：构建 child-task DAG

    Python Orchestrator wrapper → C++ hierarchical Orchestrator.submit_next_level / submit_sub；保存统一 TaskArgs、权限/依赖和 callable identity。

  3. C++ hierarchical Worker / Scheduler

    按父 run 顺序和 DAG 就绪性，把 task/control frame 送到 NEXT_LEVEL mailbox 或 remote endpoint；不是直接 launch AICore。

  4. 跨进程：Python chip child loop

    读取 frame identity、pipeline lease、callable digest；解析 TaskArgs blob、materialize 本地参数；_submit_chip_run_materialized 进入同一 ChipRunLane。

  5. 落到芯片共同执行

    与 L2 使用同一 ChipWorker/native run/runtime .so，实例位于 child。TMR/HBG 的芯片图仍在更低一层，不能把 L3 child DAG 当成它。

  6. 结果回到父 run

    child 发布接受/完成/错误；父 run 还可能有 domain/remote/host 清理。父 RunHandle.wait 管父 run 的终态与这些逻辑引用。

  1. 现有入口：内部 _ChipWorker / C++ ChipWorker

    _ChipWorker.init(..., borrowed_context_generation=非零) → C++ ChipWorker.init → simpler_kernel_mode_init。借用 caller 已建立且当前有效的 RTS context；固定 main 已由 #2599 经公共 Worker.init 转发该选项，兼容 ChipWorker 保持原入口。

  2. 注册和提交：仍走共同执行

    simpler_register_callable；_submit_chip_run_direct(..., caller_stream=...)。此入口要求合法 caller stream，在 prepare/admission 前拒绝 capture。每次 eager 调用重新准备，不重复 submit 一个 PreparedCall。

  3. 参数与资源

    caller 提供 DEVICE 地址并保持外部 allocation 存活；runtime 管自身代码、metadata、stream/event 和 workspace。HBG 可消费显式 HOST/NONE 控制数据；kernel 不承担 HOST/H2D tensor 搬运。

  4. caller 前序 → 本次两侧执行 → caller 后序

    platform 把 caller 与私有执行流接成闭合依赖。direct submit 成功返回前已入队，并建立 caller 出口等待；不允许返回 prepared-only 后让 caller consumer 超车。

  5. 共同 handle 完成与关闭

    native poll/wait/finalize 按同一生命周期退休，借用 close 不 reset caller 设备。错误 current context 的拒绝不应消费 run。主线 #2587 已保留 process/incarnation/context generation/device/policy，并用于 source 绑定验证；它不探测外部 reset，不证明任意地址归属。

  6. 能力边界

    这是 native/内部 eager 路径，不是完整公开 Worker kernel mode。旧 simpler_kernel_mode_launch 恒拒绝、simpler_kernel_mode_supported 仍为 0；capture/replay 尚未交付。#2580 的实板验证只桥接 native run 到 Python handle，不冒充完整公开入口。

direct L2 ↗L3+ ↗chip child ↗prepare 中发布 ↗caller 合同 ↗

不能把“prepare / publish 已分函数”写成“prepare 已无设备操作”，不能把 native borrowed eager 的可用性写成公共 Worker kernel eager 完整交付，也不能把 kernel mode 与 capture 混为同一维度。

6. 层次设计审查与确定的重构建议

值得保留：统一参数/公开 handle、hierarchical 与 chip 的职责分离、共同 ChipWorker/lane、opaque host ABI storage、run-bound HostApi、runtime 算法与 platform adapter，以及按最后使用者退休的资源合同。评审结论不是“层数越少越好”。
R1 · 高优先级

公共入口与内部适配混在一起

代码事实：主线 #2589 已让 direct L2 Worker 直接持有 native，保留自己的 registry/imports/lease/close journal。#2595 已让 child 直接持有 native；#2593 的 base communicator 控制句柄属于 serve loop。#2597 已统一描述符解析→POD 构造；各生命周期 owner 保留权限/保活检查。公开兼容 ChipWorker.run 仍将 DEVICE 操作数转向 Worker(level=2)，已合入 #2599 向公共 Worker 转发借用选项。

确定建议：以 Worker 作为主公共执行入口；现有公开 ChipWorker 保留兼容适配。Worker 内部只依赖一个明确的芯片执行 interface，复用已有 _ChipWorker/ChipRunLane，停止到处穿透 _impl。不要再加一组 *_kernel 后缀方法，也不要为移除 wrapper 新建 executor。

R2 · 高优先级

跨层错误不包含足够的生命周期语义

代码事实：C ABI 用数值状态，主线 #2581 已将 current-context 拒绝分类保留到 native/binding/Python wait，移除 callback。主线 #2582 已保护具体状态承诺点；#2584 已合入变更收口到共同 lease，锁外校验并覆盖 native 内存/IO。

R3 · 高优先级

资源差异还体现在两组 C ABI 名字中

代码事实：owned 用 simpler_init，borrowed 用 simpler_kernel_mode_init；注册/prepare/launch/poll/wait/finalize 已逐步共用。旧 kernel_mode_prepare_callable/launch/supported 仍被解析，launch 又是拒绝 stub。单个 supported 位无法说明 native borrowed eager 已具备哪些能力。

R4 · 已部分交付

环境身份已具备 source 消费者

代码事实：主线 #2587 在 native 上保留 process/incarnation/context generation/device/policy；Buffer source、descriptor 和 acquire 比较同一身份。成功退休清除，失败保留供重试。已合入 #2599 接 public borrowed provider；逻辑身份不能替代 RTS current-context 验证或外部地址归属证明。

R5 · 中优先级

动态模块加载知识分散在 ChipWorker

代码事实：大量符号解析、函数指针、required/optional 判断和运行控制同在 ChipWorker。header 顶部把 validator/caller entry 放在 required 清单，loader 却允许 owned legacy module 缺失，仅 borrowed init 强制存在。合同的支持与版本判断不够集中。

R6 · 中优先级

Worker 的 facade 同时承担大量领域实现

代码事实：Python Worker 同时处理 hierarchy startup/close、Buffer owner/provenance/import、remote sessions、CommDomain、callable registry 和 run finalization。C++ ChipWorker 也横跨 loader、执行、内存、通信、DFX。拆文件本身不会减少这些耦合。

确定建议：先按资源 owner 与关闭责任委托内部 module：Buffer/import、拓扑/transport、callable registry、run 生命周期。facade 保留一套 admission/close fence，统一确定顺序；被委托 module 不各自复制 Worker 生命周期。native module loader 和执行域分别拥有自身资源，但 close 的失败保留合同必须统一。

R7 · 中优先级

参数层与设备 ABI 要继续区分

代码事实：统一 Tensor 携带 BufferDescriptor 的身份/几何，运行位置解析后才得到内部 ChipTensor 的地址；这些表示服务不同 seam。未接线的 SimplerKernelInvocationHeader 声明不能被画成现有 launch 已采用的封包。

7. 推荐的最终 interface 形状

用户只面对稳定职责

Worker · CallableHandle · Buffer · Tensor · TaskArgs · RunHandle

Program 增加 owned 设备/IO provider；kernel 接入 borrowed 环境和 caller 顺序。两种资源模式共享执行。环境绑定属于 init，caller stream 属于一次 submit。

direct L2 borrowed submit 必须明确 caller stream；L3+ 的跨进程/remote 队列不能直接转发一个本进程 RTS 指针。现有公开 ChipWorker 做兼容适配，不再成为新增能力的第二份公共主接口。

内部保留真实 seam

共同 C++ ChipWorker/lane → runtime module → C ABI → algorithm/platform → RTS/device

native phase 用于真实排队、发布/执行依赖和退休；dynamic loader 是资源 owner；HostApi 绑定本次 run。binding 只适配值、handle、GIL 和错误，不自行决定能否回收 device 资源。

HBG host 构图和 TMR device 编排保留差异。捕获保存 host 最终产物、顺序和寿命，不把 Python graph builder 放到 replay 热路径。

建议先收口现有 interface；不要把图中的每一项都机械新增成一个类、一个 so 或一个公开 handle。

8. 融合后的步骤与 PR 边界

主线保留 Pipeline A → kernel eager → capture/replay。以下内容直接从 kernel-eager-open-work.md 生成；全路线状态由 ROADMAP HTML 维护。#2582 状态边界已合入；#2584 lease 汇聚已合入，K2a 完成；#2587 环境/source 与 #2589 direct L2 已合入；#2595 child 原生调用已合入；#2597 共同 materialization 已合入；已合入 #2599 接 public borrowed eager；已合入 #2604 补齐空调用与持久 INOUT；已合入 #2606 验证显式跨 caller-stream DEVICE 数据链；当前推进 S3 最小能力合同。

K2a：共同拒绝与失败合同

共同 C++ 执行层与 binding 对环境拒绝给出稳定、可机器判断的分类，沿用现有阶段与提交进度，不让上层解析异常字符串。公开 façade 仍负责自己的逻辑引用与状态变更；在提交/关闭承诺之前调用同一环境检查，native 也保护自己的状态。一个共同判定可以在两个状态 owner 的入口重复执行，不能各自发明一份规则。

情况 调用状态 / 资源 对上层的合同
环境、参数或 capture 前置拒绝；未接受该操作 原有 run/handle/source 引用不变；本次未入队取得的临时引用可按证明退回 恢复环境或修正参数后可重试；不能 poison 或把旧 run 终结
真实执行失败，已有完整完成证据 发布该次终态；按各类最后使用者回收 重复 wait 得到同一执行错误；不能伪装成环境拒绝
部分入队或设备完成未证明 保留已入队资源和使用引用，隔离执行域 失败不是撤销许可；不能因异常已经抛出就 free/unload
close 已接受但 teardown 未结束 Worker 逻辑关闭保持终态，保留环境和 cleanup debt 后续 close 可重驱债务，不能回 READY 或换设备重初始化

K2a 必须覆盖 wait/result/done、submit/admission、register/unregister 和 close 的相关拒绝；不重写全部设备错误码，按真实状态 owner 拆分：

  1. #2581（已合入）：共同分类和等待消费。 ChipWorker::validate_execution_context 抛 ExecutionContextRefused，nanobind 保留 RuntimeError 子类，规范公开导入为 simpler.task_interface.ExecutionContextRefused。Python wait/result 识别该分类，不发布终态；只有这些相同负例通过后才移除 #2580 callback。C++ phase/poll/wait/close 共用已有 guard；错误消息相同的普通 RuntimeError 仍是终态，native owner 销毁后的 lane poison 也不是可重试拒绝。

  2. #2582（已合入）：Python 状态承诺边界。 在公开 submit/admission、register/unregister、close 修改各自逻辑状态之前消费同一环境判定；不得让未接纳的 current-context 拒绝 poison source，或先关闭 façade 再发现拒绝。检查 done 的传播及 native/C ABI 注册返回路径，补齐拒绝后的恢复负例。部分入队与已经接受的关闭债务按原证明保留，不能用 blanket except ExecutionContextRefused 回退已经接纳的状态。

  3. #2584（已合入）：结构性汇聚。 _operation_lease 在持有临时 lease、释放生命周期 CV 后调用同一 native 谓词，再进入 API body；拒绝经 finally 退回 lease。所有新 leased API 默认覆盖，只有 device_location 显式豁免 current RTS context（它仍持有生命周期 lease）；close 保持独立承诺点。native malloc/free/copy_to/copy_from/device_memory_info/flush 也守自己的 backend entry；缓存 host counters、地址与 workspace/teardown reports 仅作观察。裸 C ABI 与 legacy HCCL borrowed 能力未扩充，不能据此声称完整 borrowed API 已资格化。

该历史节点第 3 笔已合入并完成本地验收，K2a 结项；当时 K2b 仅部分交付（当前交付状态见下节）。#2582 验证为 3222 Python UT、317 C++ targets、L2 sim 6/3 项和 task-submit 44 项；最终提交重建后 206 项通过。故障脚本独立保留失败预算，已接受的 close debt 在错误环境下保留、恢复后可清理。没有扩大 capture 或公开 borrowed 资格声明；之后进入 K2b。K2a 不新增 caller API、不交付 generation、不重排 Pipeline A 的准入和双侧完成协议。

K2b：借用环境与内部接入——身份必须有消费者

当前 #2587 已合入：native 记录 process、非重复 incarnation、context generation、device 与 owned/borrowed 策略；source 的 wrap/descriptor/acquire 比较同一 native 身份。成功 teardown 清除，失败 rollback/teardown 保留供 cleanup retry。当前 RTS identity 仍由既有 runner 判定，不能把逻辑 generation 当 RTS reset 探测器或地址所有权证明。此笔交付时 source provider 仍是 Program Worker；后续 #2589/#2593/#2595/#2597 已闭合 K2b 的内部接入。公开 borrowed provider 已由 #2599 接线。

2589 已合入（验证 head 27098ab9）：direct L2 Worker 直接持有 _ChipWorker，既有 Worker registry、operation lease、imports、source uses 和 close journal 继续负责原有状态。此交付时公开兼容 ChipWorker 和 forked chip child 仍走 wrapper。_initialize_chip_runtime 仅共用日志/路径/原生 init 参数转换，不另建 executor 或生命周期 owner。#2593 已合入，沿真实 child 控制消费者收口通信句柄状态：init 成功才发布新值，失败保留旧值，alloc/release 显式消费；native 保留物理资源所有权。#2595 已移除 child 的 wrapper 穿透；#2597 已统一四处 materialization，保留快照、入口前置授权和原 registry 寿命。

在原 Worker/ChipWorker 的生命周期中建立一份环境绑定，关联 RTS context identity、进程、非零逻辑 context generation 与 owned/borrowed 权限。所有环境使用和 source attachment 都验证同一份绑定。设备 ordinal 只是选择信息，不能作为外部地址授权。

  • context generation、pipeline lease generation、run_epoch、Buffer generation 分别保留语义。旧环境 source/handle 不因同 device、同地址或新 Worker 而复活。
  • source-side Buffer.wrap 继续使用统一 Buffer/Tensor；submit 在目标侧授权并取得使用保留。外部 allocation 的物理所有权仍归 caller；不用 Python Tensor 引用计数冒充 allocator 保活。
  • Worker 内部收口到既有 _ChipWorker/ChipRunLane 的一个芯片执行 interface；统一 direct L2 与 chip child 的本地 materialization 入口。公开 ChipWorker 留兼容适配，不再作为新增功能的第二个公共主接口；不添加纯转发 executor。
  • 初始化内部使用共同环境请求和资源策略；既有 simpler_init / simpler_kernel_mode_init 保留兼容接入，register、run phase、退休共用。不为收口再增加第三套执行 C ABI，旧 kernel launch stub 不恢复成另一套 runner。
  • K2b 不单独开放一个只能 init、不能按 caller 顺序执行的公共 borrowed Worker；K2c 接完整公开调用。

K2c：公开接入与完整 eager 验收

同一 public Worker 的 init/submit 接资源环境和本次 caller 顺序；环境属于初始化，stream 属于一次提交。owned 默认保持既有行为，direct L2 borrowed 提交要求显式 caller stream；L3+/Remote 不能接一个本进程 RTS 指针并跨 fork/网络传递。

统一 TaskArgs/Tensor/Buffer，使用 K2a 的拒绝合同和 K2b 的环境/source 生命周期。每次 eager 重新准备并提交一次；不引入 PreparedCall、重复 submit 或整次准备缓存。HBG 每次 fresh host 编排，TMR device 编排；kernel 拒绝 tensor H2D，不能隐藏 device→host 决策再续发。

验收必须经过真实 public Worker.init → Buffer.wrap/Tensor/TaskArgs → Worker.submit → RunHandle，不能以 private binding 或手工桥接代替。TMR/HBG × A2/A3/A5 覆盖：caller 前序写→两侧 kernel→caller 后序读、两 caller stream 的显式连接、context/generation 拒绝与恢复、外部地址/source 关闭竞争、host 值寿命、有效 callable 保留、部分 enqueue、close debt 与不 reset caller。Program 同一路径回归；权重/KV/MTP 状态显式 IN/INOUT，不进 workspace reset。

框架有后台发射队列时，adapter 必须在同一有序队列进入 native enqueue，并保持排队期参数与 allocation 引用；调用线程直接提交的测试不代替此验收。TQ=0/1、真实 enqueue 返回合同和 caller 后序均须成立。K2c 完成后才交付公共 kernel eager 可用状态，之后进入 capture。

S3：动态模块与能力合同——可并行，C2 必须依赖

当前实现候选先交付最小能力查询与 loader 校验：onboard flags=owned+borrowed+caller ordering，sim flags=owned；capture bit 恒关闭。旧模块无查询时只保留普通 owned profile；坏 ABI、失败查询和缺失所需能力在 context 创建前拒绝；拒绝不消耗初始化，允许重试。值快照属于 ChipWorker，清理后清除。下面的 module owner 与最后使用者保活仍须完成，不能把一个查询入口写成 S3 完成。

把既有 dlopen/dlsym、required/conditional 符号、函数指针和 DSO 寿命收口到 ChipWorker 内部 module owner。它是资源 owner，不是另一个 runner，也不要求另打包一份 C++ SDK so。

能力声明分别表达 owned/borrowed 环境、native caller ordering、capture/replay；以有版本/大小的最小能力查询集中校验，不用符号存在推定 stub 支持。旧 kernel supported 位只描述旧入口，不能作为公共 K2 交付门。静态模块能力与每次“现在可否 join”分开，后者仍受配置、资源与当前状态约束。

本次选择保留现有执行 C symbols，并在内部按职责分组；不新增一张覆盖全部 API 的 get_api 函数表。兼容旧 Program 模块的 loader profile 必须明确，旧模块缺少能力查询时不得猜测 borrowed/capture 支持。run、有效 callable、graph 和在飞 replay 持有 module 资源；卸载早于最后引用是验收失败。unknown completion / close 失败须保留正确的 module 与环境，不随 C++ wrapper 析构误 unload。
