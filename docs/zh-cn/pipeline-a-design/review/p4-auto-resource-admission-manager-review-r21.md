# 自动资源准入 r21：设计收口评审

设计归档快照：状态与阅读顺序见[索引](../README.md)。设计约束、历史合同和当前实现须分别阅读。

状态：完整设计可进入具体实施决策；尚未批准实施，未执行测试。基线 cc6c4d51f，原作者 r21，经理核对 r20→r21 全量差异及相关状态机。

## 接受的闭环

- 固定每阶段首次等待的 holder 身份集合；消费过的退休身份不再等待，不因容量下降重新扩大集合。每阶段至多 D−1 次资源等待；不按当前可收缩的 admission_depth 作界。
- 每次恢复至多两次事务尝试；每阶段至多 D 次激活。两阶段累计至多 4D 次事务尝试，最多 8D 次底层分配调用，不存在定时重试。
- 正常运行但尚未退休的消费者是可等待对象；隔离、释放失败、保留映射、失败后停止未知均不可作为释放保证。
- 本步是四个 onboard 后端的本地 L3 默认自动准入完整功能，不能拆成多次增大固定数字的 PR。Qwen 外部 driver 不重复实现。

## 经理收口勘误：实施合同以本节为准

1. r21 §8.4 留存的“两次 allocator calls per phase”应读作 §9.3 的“每次激活至多两次事务尝试”。§14.1 的 trim 也按激活计数，不能声称每阶段仅一次。§9 原列表的 unproven 用语以 §9.2 的失败后停止未知为准。§9.3 的半句重复排版无新增语义。
2. 等待状态的内存不能报成总共仅 D−1 个身份：S/C 两个快照及跨阶段 consumed 需要分别容纳；实现应选择当前快照加已消费身份/位图，按实际布局报告总量，保守计至多 2(D−1) 个不同身份及成员标记。每槽同阶 O(D)，不是 8(D−1) 字节总成本承诺。§5 示意结构应补齐 §9.1 的真实状态。
3. **错误码不能照抄草案的 BASE−3/−4。** 当前 runtime_c_api.h 已用于 INVALID_STATE / INVALID_ARGUMENT；#2588 使用 BASE−5 作 DIAGNOSTIC_CAPACITY_FULL。实施须分配不冲突的新符号和值，禁止新增 PTO_ / PTO2 命名，保留既有 ABI；覆盖数值唯一性和 typed exception 分支。
4. 64 KiB 目录预算推导的 D 当前为168，是内部有限身份表上限，不是设备字节预算、用户参数或全部可运行数量。实际容量从1启动，资源证明和退休更新后逐步增长，达到表上限仍背压；不宣称无限深度。
5. new set 的 event/主机缓冲等不属于四类 ledger；这些资源失败仍明确失败。本步不声称全设备 OOM 自动恢复或降低延迟。

这些是同一方案的勘误及实现约束，不新增架构轮次；不再为排版、符号占位和成本表开启另一作者设计任务。具体决策见 [实施合同](p4-auto-resource-admission-decision.md)。原作者保持 idle，批准后按最新 main/open PR 门禁实施。
