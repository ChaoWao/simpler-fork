依据：用户明确要求“这个图要变成KernelArgs的方式传进去……rts会copy”。本合同替代已撤回的图定义设备块扩容保全方案。

## 现在为何需要改

主机先构造一份图定义：子任务清单、依赖关系、子任务参数描述和相对位置。现在 runtime 自己申请设备块，将这份定义 H2D 上传，再把设备地址交给 AICPU。跨次运行还要处理这块存储的扩容、复用、释放和失败。

本次把完整图定义放入 AICPU 的 launch 参数包，由 RTS 复制和持有参数存储。runtime 不再为图定义单独 rtMalloc、上传或 rtFree。这里搬的是图的描述，不是用户 tensor 的数据；用户传入地址的释放权和调用方寿命约定保持。

## 一次运行如何工作

1. 主机构图后，打包本 run 的完整图定义字节。保留 host staging 和独立参数快照，图内引用用偏移表示。
2. 实际 AICPU launch 传入 KernelArgs 头和图定义区，argsSize 包含全部字节。沿用现有两条 stream 的提交顺序和 run 资源寿命；RTS 负责设备参数副本。
3. 每个 AICPU 读取线程从自己的参数视图读取，不把某个线程的参数地址存进共享执行状态。解码按字节复制到对齐的局部值，不要求 RTS 参数基址具备未被保证的对齐。
4. 后续调度线程反复读取的依赖索引，按值放入该 Graph 已有执行存储尾部；它随本 run 的工作区退休。其他图内容继续从当前读取线程的参数包读取，不另建整图设备副本。
5. 完成或异常沿既有终态、排干和退休路径处理。一个线程返回后，其他线程不再借用它的参数地址。

## 范围和兼容

- a2a3/a5 onboard 的 HBG program Graph 路径；A5 必须接实际使用的 legacy executor。
- 两端 sim 同步适配。sim 没有 RTS launch 包，显式使用由 runner 持有至本 run 结束的 host 快照，不能宣称是 RTS 复制。
- TMR 已有参数载体、无 Graph 的路径、用户 tensor 所有权、设备串行及默认调用语义保持。不开放 capture，也不接管外部主线。
- 新共享头、图描述和执行存储布局需要 host/AICPU/AICore 及相关扩展一致重建。保留既有外部接口；不新增 PTO_/PTO2 标识符。
- 与 #2481 有共享文件重叠，按实际合入顺序集成，不能覆盖对方的提交/完成/引用退休语义。

## 资源和失败代价

图定义字节仍要传输，只是从 bind 的单独 H2D 移到 launch；可能减少与前驱执行的上传重叠。增加 host 打包/快照和逐元素解码工作，不承诺延迟或吞吐收益。

每个 Graph 的现有执行存储增加依赖索引，原始内容约为 `(任务数 + 1) × 4 + 依赖边数 × 2` 字节，另计对齐及布局变化。这些空间必须纳入原有 host/device 一致的容量计算；不新增独立图定义设备块。RTS 内部副本数量与实际分配成本未核定，不承诺总设备内存下降。

不人为添加图大小上限；检查 argsSize 的32位可表达范围及所有长度运算。RTS仍可能分配或提交失败。打包失败在 prepare 阶段返回；若 AICore 已提交而 AICPU launch 失败，按 Partial 处理，不能当作未启动。设备读到无效图时，通过既有调度错误通道结束整个 run；不新增等待所有线程到齐的屏障。

## 实现必须满足的检查

- 所有共享执行状态中的指针必须指向执行自有存储，不能间接借用任意线程的参数包。覆盖依赖数组、图描述及其下级对象。
- 解码同时检查对象范围和整个包的范围；偏移乘加先检查溢出。不能对单独复制的头继续调用旧的“头后紧邻对象”指针式校验。
- 依赖索引扩展须同步更新构图时容量计算、两个架构的 bind 校验和设备执行存储获取，容量不足不得越界写入。
- sim 的来源、长度和快照寿命显式区分；onboard 不可默默回退手动设备块。
- DFX 原图上传阶段的说明改为实际图打包阶段，不伪报已经不存在的独立 H2D。
