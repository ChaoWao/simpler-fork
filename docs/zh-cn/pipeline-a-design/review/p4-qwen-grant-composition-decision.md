## 1. 用户接口与目标

普通调用沿用 `Worker(...)` 和 `worker.submit(...)`，不要求配置 pipeline_depth、pending_run_depth、launch_depth，也不引入 grant 别名。资源管理与调度负责准备、提前入队、背压和安全回收，设备 operator 仍串行。

内部仍须分别管理逻辑请求、传输帧、执行存储、事件、输出及诊断资源。它们寿命不同，但内部存在不同额度不等于用户必须逐项配置。确有调用者主动限制占用或积压的需求时才保留可选限额；本次不先发明新参数名或强制预算。

## 2. 准入和等待规则

| 情况 | 行为 |
| ---- | ---- |
| 有安全可复用资源 | 预留并接受，满足依赖后尽早提交设备 |
| 需要增长，且资源策略允许 | 准备新资源，全部必要预留成功后发布；失败回滚本次预留，保全旧计划 |
| 所需资源被在途消费者占用，存在明确归还来源 | 等待对应资源释放事件，醒来重查条件；不中断其他请求推进 |
| 单请求不满足能力或明确额度；分配失败且无可等待释放来源 | 明确拒绝/报错，不无限等待或反复分配试探 |
| 执行停止未知或所有权受损 | 隔离资源、停止相关新发布并报错，不能当作普通压力等待 |

自动背压不等于一直 malloc 到 OOM，也不等于根据一次 free-memory 查询承诺分配成功。主机控制记录、传输、设备工作区、事件和 DFX 保留都需要有限资源策略。尚未获得资源的请求不能无限复制、排队或占用用户借用；提交前后所有权及阻塞位置必须明确。

资源释放采用事件/条件通知，不忙等；资源等待不得持有退休所需锁。多资源预留必须支持原子发布/回滚或等价的无死锁顺序，不能占住一部分再等待必须靠自己提交才能归还的另一部分。后继不兼容时沿用安全等待，不为了提前提交破坏前驱存储。

## 3. 当前实现与必须补齐的设计

\#2571 已解除固定2/3套上限，仍由配置决定启动时的资源表和mailbox状态表规模；当前默认两套资源、launch_depth=1。可配置容量不等于自动资源准入，现有历史验收不能外推新目标。

下一份具体实现设计必须给出：

1. **自动资源策略**：复用优先、何时增长、何时停止增长并等待、各类资源的计量/归还来源；内部上界或默认策略必须有依据，不能把隐藏的固定depth冒充自适应。
2. **准备前未知需求**：构图后才知道的workspace大小如何分阶段预留；准备阶段本身的host占用也须受控。禁止已承诺接受后靠无限积压兜底。
3. **表和地址稳定性**：梳理启动时定长的run表、mailbox布局、lease/身份索引。说明在线扩展、分段管理或其他方案如何在不搬动在途引用的条件下实现；不是删掉Python参数就完成。
4. **调度与兼容**：有资源、有依赖证明时尽早提交；保留parent FIFO、设备串行及各后端回退。明确旧显式depth配置的映射/拒绝规则及旧默认launch=1如何迁移，不静默改变已有调用含义。
5. **失败与关闭**：区分可等待压力、不可满足、分配失败和停止未知；证明阻塞提交与close可有界退出/报告，不新增隐式跨run host数据同步。

最终以一个完整普通异步功能PR组织实现和验收，不按删一个参数、扩一张表拆零碎交付。具体逐文件方案及成本仍需补齐；本次更新不改运行时代码、不开始新的硬件测试。

## 4. Qwen 组合验收随运行时方案调整

Qwen 应使用正常 submit 路径，不再要求用户填写4/2或用新grant选项驱动。原固定N+1缓冲算法仅是旧有限深度driver的实现策略，不能把N重新暴露给调用者。新设计须说明driver如何在准备和借用输出前获得可用缓冲，并在验证及最后消费者结束后复用；不能简单取消上限后无限创建输出帧。

复用已合入 #2471/#2511/#2568 的身份、DEVICE反馈及数值验证证据。新增验收需覆盖资源充足、可回收压力、单请求无法满足、增长失败回滚、持续补队、最后消费者和失败/关闭。确定性测试证明背压因果；真实Qwen报告token/logit/KV、joined/refill、实际占用与复用，不把提交耗时当作发生资源等待的证据。

单A3 HBG、diagnostics关闭的历史127步证据范围保留；自动模式的新范围与运行次数由具体设计明确，不外推A5/TMR、多endpoint或clone组合已通过。DFX自有额度和错误合同保持独立；capture仍只是未来约束，本次不实现capture/replay。
