## 1. 问题与目标

旧公共调用按 worker_id 选择一个 chip，返回 WorkerChipOrchRegion/WorkerChipQueue facade；Region 的六标量描述符不能携带 allocation 的 session/transaction。底层已经有 selector、planner、RegionInstanceRegistry 与模板，公共层仍编码单跳部署，并复制访问/释放入口。

本 PR 的具体目标是：L3、L4 转发及嵌在 L4 树中的 child L3 均可用自己的 registry 选择一个 Host consumer 和同节点 AICPU provider；直接拿 RegionInstance/SpscQueue；native 错误带可信 allocation identity 回到所属 run。

与我们的设计契合 RA-11 的 W4①/W6 与 RA-14 公共 surface 收敛。P3④ 的最终目标更大：既有 Buffer/slice 的受管理绑定、通用 publish/observe/wait、RA-4 可见性与 RA-7 资源基座仍不在本 PR 内。正文明确不做跨节点、多 consumer、Host/AICore provider、公开 template registry 或跨 run 生命周期；这是明确分期，不是这些能力已交付。

## 2. 实现机制

`Orchestrator.create_region(members, topology, ...)` 委托 Worker，在当前 callback/run、operation lease 和 control admission 下解析 at/under 与 SingleOwner，经过既有 BackendResolver/物化路径注册实例。queue 根据 initiator/peer 推导成员与 provider，调用既有 template coordinator；placement 在 allocation 前验证，bind/publication 失败沿 registry 回滚。child L3 保持自身 registry 根 L3；父树的 L4/L3[...] 只承担转发控制路由。

例如 child L3 的回调选择 `at("L3", HOST_CPU)` 和 `at("L3/L2[0]", DEVICE_AICPU)`，获得对象后提取 opaque scalars、提交 native 任务，再进行 payload/counter 或 queue 收发。旧 facade 入口被删除，调用方与 native consumer 必须一起迁移。

RegionInstance 记录 owning resources/run id。公共访问校验本 run、LIVE、未 free、未 poison；RegionCounter 保存 instance，因此已取出的 counter 也受 free 约束。free 只停止逻辑访问，physical close 留在 run drain 后的 ordered cleanup；未显式 free 也由 registry 清扫。SPSC 保留双向有界 arena、背压、STOP、active handle 和 abort 机制，不成为任意多生产者线程接口。

Region 使用严格 8 个 uint64 的 ABI 4，新增 session bits 与非零 transaction；应用参数从 index 8 开始。SPSC 保持精确 10-scalar SPSQ 1.0。native decoder 对 magic/version、范围、独立 payload/counter span 和 transaction 校验。旧六字段 decoder 与兼容 fallback 删除。NativeRunDescriptor 增加 host-only identity sink 指针，PipelineContract ABI 1→2，并同步 Python 测试镜像；runtime 与 consumer 均需重建。

失败身份先由 endpoint diagnostics 交给 runtime：TMR 将首个 fatal 的 POD identity 放到 SharedMemoryHeader 的既有尾部；HBG 经 OrchestratorState 交给 HostApi。ChipWorker 为每个 pipeline slot 分配 sink，构造短 marker；Python 严格解析 session/transaction，匹配当前 run 的唯一实例，不回退 resource id。未知、重复或畸形身份使 admission fail closed。问题在于 sink 按 slot 存储，但 finalize 的消费没有与 slot 再分配共用临界区。

## 4. 缺陷、验证与边界

### 必修：P2，finalize 在 slot 释放后读取/清空身份

位置：[chip_worker.cpp:1644](https://github.com/hw-native-sys/simpler/blob/850a36bd9cfd14a77683a12f58d5b0b778cda080/src/common/worker/chip_worker.cpp#L1644)，成功分支同样见 1627；释放点在 [1797](https://github.com/hw-native-sys/simpler/blob/850a36bd9cfd14a77683a12f58d5b0b778cda080/src/common/worker/chip_worker.cpp#L1797)。

确定的交错如下：旧 run A 在 finalize_native_run_epoch 内销毁 carrier，持 native_run_mu_ 从 native_runs_ erase，然后解锁；线程 B 在同一 slot 成功 prepare，写入 B 的 endpoint identity；A 回到 finalize_native_run_impl。A 若失败，读取的是 B 的身份，并把它附在 A 的错误上；A 无论成功或失败都可清掉 B 的 identity。B 的写与 A 的锁外访问还构成数据竞争。prepare 端已把初始清零挪到 admission 后，无法保护 finalize 尾部。

修复应在 slot 仍归 A、同一把 mutex 内快照并清理 A 的 identity，把值放进 NativeRunFinalizeOutcome，然后才发布 slot 可复用；外层仅消费 outcome，不能再按裸 slot_id 回读。非销毁/未知销毁与重试路径须保留其寿命约束。补充有 barrier 的“finalize A 与同 slot prepare B”回归，覆盖 A 成功、失败两种返回。

本地已运行确定性 C++ 调度 harness：直接提取 head 的 finalize_native_run_impl 和 marker formatter；用 stub 模拟真实 erase/unlock 后的合法 slot 复用窗口。阳性对照无复用时报告 transaction=11；插入后继 transaction=22 后，旧失败 run 报 22 并清空后继；旧成功 run 也清空后继。它验证提取函数的错误时序，不冒充完整 runtime/NPU 复现。本轮未改实现代码。

## 5. 合并建议

问题真实，endpoint 与 Region 分工也符合方向；正常链路、ABI 切换和双架构正常场景有证据。但 failure identity 的并发归属仍可被 slot 复用破坏，且最新 main 有集成冲突，因此 **request changes**。先修 identity 的快照/退休时序并补确定性回归，再解决冲突、对新 head 重跑相关 UT/ST。接受该 PR 后仍只增加 RA-11 的公共 surface 交付，不关闭父目标。
